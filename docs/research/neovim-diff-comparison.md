# Neovim diff options for corporate Windows

Research date: 15 November 2026. Current configuration: [3ea4982](https://github.com/jichong-tay/dotfiles/blob/3ea498292e268286b439d8ac9691d4b01f78dd11/nvim/init.lua). Upstream snapshots examined: `diffs.nvim` at `e313128621848cb6a244beb687272c1d542fb580`, and `differ.nvim` at `939b3c2f68e4d94455ba73ecd96743bd360ed1e6`. This is a documentation/source review with an isolated content-reader check on macOS, not an end-to-end performance benchmark or Windows compatibility certification.

## Recommendation

Keep the present setup on the corporate laptop until a candidate demonstrates an improvement there. Both alternatives remove some custom display code, but neither is an established cure for expensive Git launches. `diffs.nvim` is the smaller replacement to evaluate for review views; `differ.nvim` is closer to a complete Git review workspace, with a more substantial runtime and refresh behavior to assess. These are judgments based on the differences below.

The constraints are native Windows Terminal, Neovim reportedly 0.12.6, no administrator access or PowerShell, no local compilation, Schannel download failures, and slow Git operations. These are user-provided conditions; no security or system settings were changed.

## What the current configuration already supplies

The current file supports editable inline review and native side-by-side review, whole-file `HEAD` toggles, staged/unstaged navigation, red old lines and green new lines with darker word highlights, and custom wrapping of deleted virtual lines. It also handles LF/CRLF display differences without changing file bytes. The trade-off is custom integration with private Gitsigns rendering functions, which needs checking when the pinned plugin changes. [Current implementation](https://github.com/jichong-tay/dotfiles/blob/3ea498292e268286b439d8ac9691d4b01f78dd11/nvim/init.lua)

Windows-specific reductions are already present: a two-minute ahead/behind cache, no count queries caused by idle cursors or hidden repositories, shared pending queries, a manual count-refresh key, 500 ms edit debouncing, and reuse of an existing repository review. Git watchers remain enabled. These measures reduce repeated work; they cannot remove the cost of reading a fresh repository. [Current implementation](https://github.com/jichong-tay/dotfiles/blob/3ea498292e268286b439d8ac9691d4b01f78dd11/nvim/init.lua)

## Functional comparison

| Concern | Current setup | `diffs.nvim` | `differ.nvim` |
| --- | --- | --- | --- |
| Both layouts | Inline and native splits | Unified/stacked and plugin-aligned splits | Stacked and split |
| Editing | Working file stays editable | Generated review panes; open the working file to edit | Review surfaces; separate edit/go-to-file actions |
| Whole file | Explicit split toggle expands context | Split panes disable diff folds | Full context is the default |
| Long deleted lines | Custom virtual-line wrapping | Real review lines; split mode explicitly disables wrapping | Real review lines; wrapping defaults on |
| Repository navigation | Changed-file panel | Review map, quickfix/location lists, file navigation | Dedicated file panel, staging and history |

The alternatives' layout and editing distinctions are documented in the [diffs.nvim help](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/doc/diffs.nvim.txt) and [differ.nvim README](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/README.md). The `diffs.nvim` split wrap setting is explicit in its [split implementation](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/lua/diffs/split.lua).

Neither default backend is VS Code's algorithm: `diffs.nvim` defaults to Neovim's diff implementation for intra-line analysis; `differ.nvim` uses `vim.text.diff()`. Consequently, replacing the UI does not guarantee that the previously mismatched function definitions will pair like VS Code. [diffs.nvim help](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/doc/diffs.nvim.txt), [differ.nvim README](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/README.md)

## Installation and slow-Git implications

`diffs.nvim` documents a plain `vim.pack` installation, with no mandatory compiler or extra diff-library step. Use its default backend and existing Windows parsers; optional native backends are outside this comparison. Its generated repository review performs several synchronous `vim.fn.systemlist()` Git calls for root/ref resolution and diff data. **Inference:** slow corporate Git can therefore pause the editor during those reads, even though the plugin itself requires no build. [Installation](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/README.md), [review source](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/lua/diffs/review.lua)

`differ.nvim` explicitly allows omitting its Go build hook for local diffs; Go, make and authenticated `gh` are for PR review. Its local Git layer has an asynchronous per-repository queue and a persistent `git cat-file --batch` process, potentially avoiding repeated blob-reader launches. However, its watcher uses a 50 ms debounce and refresh checks still launch Git status before deciding whether the display changed. **Inference:** its batching is promising, but its background work may offset that benefit on this laptop. [Installation](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/README.md), [Git execution](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/exec.lua), [blob reader](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/cat_file.lua), [watcher](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/watch.lua), [status refresh](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/init.lua)

More importantly for Windows, `differ.nvim` normalizes CRLF/filter-sensitive worktree content through a temporary index: it resolves/copies the index, runs synchronous `git add` and `git show` against that temporary index, then removes it. The real index is not the target, but viewing can add Git launches and disk work. Its absolute-index-path check also recognizes a leading `/`, leaving drive-letter paths as a potential portability problem; that is a source concern, not a reproduced Windows failure. **Inference:** this makes it a poor choice to adopt solely as a performance improvement for the corporate CRLF workflow. [Content normalization source](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/content.lua)

An isolated macOS check loaded that upstream content reader and Git execution module against a temporary repository with `core.autocrlf=true`. One LF worktree-content read launched one Git command (`check-attr`); one CRLF read launched three (`rev-parse`, temporary-index `add`, and `show`). The working file and real index remained byte-identical. This checks that code path, not total review latency or actual corporate Windows behavior; other content-reader dependencies were stubbed where the worktree-only path did not use them. [Reader](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/content.lua), [execution module](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/lua/differ/git/exec.lua)

For this environment, copying plugin files and retaining compatible installed parsers avoids adding a download/build requirement; it does not prove Windows path handling works. Both examined CI workflows use Ubuntu, not a Windows matrix. Actual Windows paths with spaces, CRLF files, staged/unstaged combinations, long deleted lines, slow Git and repeated opens still need checking. [differ.nvim CI](https://github.com/undont/differ.nvim/blob/939b3c2f68e4d94455ba73ecd96743bd360ed1e6/.github/workflows/ci.yml), [diffs.nvim CI](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/.github/workflows/quality.yaml)

Any trial should replace the corresponding custom review renderer rather than layer another renderer on top. `diffs.nvim` itself warns about overlapping Gitsigns highlighting. Keep the current pinned setup available until the same representative file passes the visual and latency checks. [Compatibility notes](https://github.com/barrettruth/diffs.nvim/blob/e313128621848cb6a244beb687272c1d542fb580/README.md)
