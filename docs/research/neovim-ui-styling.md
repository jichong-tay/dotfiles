# Neovim UI polish without a new UI stack

Researched 2026-11-16 against official documentation and source. Baseline: [current configuration at 780ce6e](https://github.com/jichong-tay/dotfiles/blob/780ce6e6b37e36eef8f407bdc5b8543dde9c873a/nvim/init.lua), reported Neovim 0.12.6, `vim.pack`, Nerd Fonts on both machines, and a corporate Windows machine with restricted downloads, no PowerShell, no local builds, and expensive process launches. This is a documentation review, not a performance benchmark or Windows certification. No plugins were installed and no configuration was changed.

The user prefers a transparent editor and specifically requested a charcoal, rounded `K` hover. Keep that distinction: the editing canvas can remain transparent while temporary panels have a readable surface. A change of theme is optional; consistent surfaces and less competing bar content are the stronger first step. Recommendations and descriptions of visual character below are design judgments; documented capabilities have nearby source links.

## Prioritized polish path

1. **Give temporary panels one visual language.** Reuse the existing hover's charcoal surface, muted outline, and zero blending for Telescope and WhichKey where useful; give completion a distinct selected row. Avoid restoring gray backgrounds across the editor or embedded terminal. Neovim exposes `NormalFloat`, `FloatBorder`, and local highlight remapping; `winborder` supplies a default, but explicit plugin borders take precedence. This needs targeted plugin settings, not a new UI library. [Float API](https://neovim.io/doc/user/api.html#api-floatwin), [default border](https://neovim.io/doc/user/options.html#'winborder'), [blending](https://neovim.io/doc/user/options.html#'winblend')

2. **Let the bars have separate jobs.** Keep the top winbar's relative path, source-colored declaration, and distance. Consider removing the repeated filename from the active bottom statusline, leaving mode, Git, diagnostics, and position. Keep the real tabline as actual tabs; reduce its large pale-blue selected fill to a restrained accent/bold label if desired. The configuration already owns these renderers, so replacement statusline, breadcrumb, or bufferline plugins are unnecessary for this direction. This is a layout proposal, not an upstream preset. [Existing bars](https://github.com/jichong-tay/dotfiles/blob/780ce6e6b37e36eef8f407bdc5b8543dde9c873a/nvim/init.lua#L1613)

3. **Add one quiet scope cue.** Start with `mini.indentscope` already available in the installed mini.nvim package: a thin, muted guide with animation disabled. It computes scope from indentation rather than syntax, permits per-buffer disabling and a scan limit, and supports `gen_animation.none()`. Disable its mappings for a visual-only trial: its default `ii` collides with this configuration's `mini.ai` `inside_next = 'ii'`. It also supplies `ai`, `[i`, and `]i` by default. [Official module documentation](https://nvim-mini.org/mini.nvim/doc/mini-indentscope.html)

4. **Clarify focus with small cues.** Keep a visible but subdued `WinSeparator`, brighten the active winbar/basename, and retain a distinct inactive winbar. Prefer these cues before dimming whole inactive panes, which can change the desired transparent appearance. Native `winhighlight` can remap groups per window; vertical separator coloring is determined by the window on its left, so a focus-colored outline is not a free global switch. [Window highlight rules](https://neovim.io/doc/user/options.html#'winhighlight')

5. **Restyle the picker you already have.** Use a consistent rounded frame, charcoal prompt/results surface, and clear selection. Keep a wide preview for grep/references and the existing dropdown for small choices. Telescope documents border characters, prompt position, preview cutoffs, and dropdown/ivy themes; WhichKey offers `classic`, `modern`, and `helix` presets plus window padding and border settings. Try those before replacing either plugin. [Telescope styling and themes](https://github.com/nvim-telescope/telescope.nvim/blob/master/doc/telescope.txt), [WhichKey options](https://github.com/folke/which-key.nvim#%EF%B8%8F-configuration)

## Three coherent visual directions

All three can retain a transparent editor. Palette swatches below are documented theme colors, not a promise of contrast on the user's actual terminal background. Judge comments, selection, diagnostics, and source-colored declarations on both terminals; screenshots with opaque backgrounds will not reproduce the transparent result. The official previews are [VS Code](https://raw.githubusercontent.com/Mofiqul/vscode.nvim/main/demo.png), [Mocha](https://user-images.githubusercontent.com/56817415/213471997-34837219-88cc-4db2-baca-e25813a89789.png), and [TokyoNight Night](https://user-images.githubusercontent.com/292349/115295327-7afdce80-a10e-11eb-89b3-2591262bf95a.png); they can include extra plugins and layouts and are not complete configurations to copy.

For terminal Neovim, font face/size and actual desktop transparency are terminal settings; disabling the theme background exposes the terminal's chosen surface. Windows Terminal documents font and opacity controls separately. Keep the current terminal-color policy when trying themes: `terminal_colors = false` for VS Code/TokyoNight, `term_colors = false` for Catppuccin. [Windows Terminal appearance settings](https://learn.microsoft.com/en-us/windows/terminal/customize-settings/profile-appearance)

Check the actual terminal's true-color support for faithful RGB palettes; Neovim's `termguicolors` controls 24-bit TUI colors. Catppuccin also calls this out explicitly; no blanket conclusion about the user's macOS terminal version is assumed here. [Neovim color option](https://neovim.io/doc/user/options.html#'termguicolors'), [Catppuccin FAQ](https://github.com/catppuccin/nvim#why-arent-my-colors-the-same-as-the-previews)

For either new theme, migrate the custom bar, hover, and diff highlights deliberately. Existing hard-coded pale-blue/green badges and mode-driven winbar colors will otherwise mix with the new palette; the source declaration also borrows editor highlighting. Do not infer the final appearance from the theme's standard screenshots. The documented install steps for these themes have no local native-build hook; initial acquisition still needs a permitted download or transfer. [VS Code installation](https://github.com/Mofiqul/vscode.nvim#%EF%B8%8F-installation), [Catppuccin installation](https://github.com/catppuccin/nvim#installation), [TokyoNight installation](https://github.com/folke/tokyonight.nvim#-installation)

Catppuccin's “compile” feature means caching computed highlights in a Lua file; it does not require GCC or a native plugin build. [Compile documentation](https://github.com/catppuccin/nvim#compile)

## Scope and word highlights: choose deliberately

`mini.indentscope` is the first trial because the package is already present. **Indent Blankline (`ibl`)** is appropriate when faint guides for every indentation level are wanted, rather than one active guide. It renders with virtual text, supports blank lines and mixed indentation, and its syntax-aware scope needs Tree-sitter. Its README requires the latest stable Neovim and documents `vim.pack`; reuse compatible existing parsers on Windows rather than introducing a parser-build task. Do not enable two competing scope renderers: mini's documentation explicitly notes their drawings can obscure one another. [ibl README](https://github.com/lukas-reineke/indent-blankline.nvim#readme), [mini comparison](https://nvim-mini.org/mini.nvim/doc/mini-indentscope.html)

`mini.cursorword` is an optional readability aid already available in mini.nvim. It highlights Vim words, offers a configurable delay and separate current-word styling, and stops in insert/terminal modes. It is lexical matching, not LSP symbol-reference analysis; repeated names can therefore light up outside the current symbol's scope. Trial a modest underline only if current LSP reference highlighting is insufficient. [Official documentation](https://nvim-mini.org/mini.nvim/doc/mini-cursorword.html)

## Why defer broader replacements

**Noice + Nui:** useful if the actual goal becomes a floating command palette, routed messages, or searchable message history. Noice requires Neovim ≥0.9 and Nui; notify, Nerd Fonts, and Tree-sitter are optional, with parsers recommended for richer highlighting. Upstream still labels its `vim.ui_attach` usage experimental. Its default LSP progress/hover handling overlaps with the current Fidget and custom hover. Nui itself is a component library, not an automatic makeover. These are additional integration decisions for little benefit to the five changes above. [Noice requirements and defaults](https://github.com/folke/noice.nvim#readme), [Nui](https://github.com/MunifTanjim/nui.nvim#readme)

**Snacks:** offers configurable picker layouts and `vim.ui.select`, indent/scope guides, input, notifications, and terminals; core requires Neovim ≥0.9.4 and modules are explicitly enabled. That can justify a coordinated replacement later, but overlaps Telescope/ui-select, prospective mini guides, and ToggleTerm here. A concrete Windows concern: picker database configuration can download SQLite, and the current DB loader invokes PowerShell when the DLL is absent and no path is provided. This is conditional on DB-backed functionality loading, not proof every picker downloads it. A cosmetic-only adoption is difficult to justify under these constraints. [Core modules](https://github.com/folke/snacks.nvim#readme), [picker options](https://github.com/folke/snacks.nvim/blob/main/docs/picker.md), [Windows DB loader](https://github.com/folke/snacks.nvim/blob/main/lua/snacks/picker/util/db.lua#L19)

## Evaluation order

First compare the existing VS Code setup with unified panels, reduced bar duplication, and a static scope guide. Then compare Mocha and Night on the same source file, split layout, hover, picker, diagnostic, and Git review. Check readable comments and selected rows, retained diff distinctions, narrow panes, and absence of new downloads/process launches on Windows. Documentation establishes available controls; it does not establish which option is faster on the monitored laptop. Keep changes only when they improve an actual working view.
